# Stripe test-mode validation environment (plan; nothing provisioned)

Purpose: prove the account-first checkout (branch `feat/billing-security-prep`) against REAL Stripe test mode and a REAL, separate
database before it goes to production. **Nothing in this document has been created or changed.** Never use production Stripe keys,
live prices, production customers or the production database for any step. No secret value belongs in this file or in chat.

## 1. Minimum setup

| # | Need | Why | Who |
|---|---|---|---|
| 1 | **Stripe test-mode secret key** for ALPA's Stripe account (`sk_test_...`) | Checkout sessions, customers, subscriptions in test mode | Owner: Dashboard, toggle "Test mode", Developers, API keys |
| 2 | **Two test-mode recurring prices** matching the live Starter ($29.99/mo) and Prospector ($9.99/mo) plans | `STRIPE_STARTER_PRICE_ID` / `STRIPE_PROSPECTOR_PRICE_ID`; the plan of a subscription is decided by its price id | Owner confirms the live amounts; the prices can be created in the dashboard, or by me with `stripe prices create` once a test key is available |
| 3 | **Webhook signing secret** (`whsec_...`) | The webhook verifies every delivery's signature | Free: `stripe listen --forward-to localhost:3000/api/stripe/webhook` prints a test signing secret (needs `stripe login`, a browser pairing by the owner, because the CLI's saved test keys expired on 2026-07-01) |
| 4 | **A separate Supabase project** (the test database) | Accounts, profiles, leads, guest trials; production must never be touched | Owner creates it (see section 3 for the schema and cost) |
| 5 | **Test project auth settings** | Site URL `http://localhost:3000`, redirect allow-list `http://localhost:3000/**`, "Confirm email" ON (needed for the signup-and-confirm scenario) | Owner (dashboard, Authentication) |
| 6 | **Local env file** `.env.stripe-test` from `.env.stripe-test.example` | The app reads these variables | Owner fills in TEST values only; I verify with `scripts/test-env/check-isolation.mjs`, which prints yes/no and never a key |
| 7 | **Dedicated test accounts** | Never real customers | Created in the test project by the scenarios (addresses like `billing-test-a+1@<owner mailbox>`; confirmation links can be generated by the test script, so no mailbox access is needed) |

Return URLs need no Stripe setting: checkout builds them from `NEXT_PUBLIC_APP_URL` (success `/post-checkout?session_id=...`, cancel `/plans`), so with
`NEXT_PUBLIC_APP_URL=http://localhost:3000` Stripe returns to the local app.

## 2. What already exists and can be reused

- **Webhook route** with signature verification (`app/api/stripe/webhook/route.ts`) and event handling for checkout completion, subscription updates and deletion, paid and failed invoices. Now covered offline by `tests/stripe-webhook.test.mjs` (valid, missing, wrong-secret, tampered and replayed signatures, using Stripe's own verification code).
- **Offline model of Stripe and the database** (`tests/billing-journey.test.mjs`, `tests/fixtures/billing/world.mjs`): the same 9 checks that the real run repeats against Stripe.
- **Stripe request blocker** `tests/helpers/stripe-sandbox.cjs`: launching the app with `NODE_OPTIONS=--require tests/helpers/stripe-sandbox.cjs` makes every Stripe request fail, which is how the Stripe-outage scenario is run.
- **Isolation guard** `scripts/test-env/check-isolation.mjs` (new): refuses a live Stripe key, the production Supabase project (`hnhptr…`), a missing price or webhook secret, a non-local app URL, and any paid-provider key.
- Stripe CLI 1.40 and Supabase CLI are installed on this machine.

## 3. What is missing, and the one real obstacle

1. **No test-mode credentials** exist in the project environment (only a live key); the CLI's saved test keys are expired. Needs items 1 to 3 above.
2. **The core database schema is not in the repository.** `supabase/migrations` (44 files) only adds to tables that were created earlier by hand; `supabase/schema.sql`, which the README mentions, was deleted. A fresh Supabase project therefore cannot be built from the repo. Options:
   - **A (recommended): a read-only schema extraction from production** (tables, columns, constraints, indexes, functions such as `handle_new_user`, triggers, row-level-security policies, grants) turned into `supabase/test-env/schema.sql` and applied to the test project. It reads the catalog only and copies no data. I can do it with the access I already have; it touches production only by reading. Estimated 2 to 3 hours including a check that the test project's catalog matches.
   - B: Supabase local stack (Docker). Not realistic on this machine at the moment: Docker did not start reliably and the disk has under 1 GB free.
3. **Cost of the test project:** the organisation already has six projects, so a seventh is billed as a new project on a paid organisation (about $10 per month while it exists; it can be paused or deleted afterwards). Needs the owner's approval.
4. **Paid providers are not needed.** Scenario 1 uses a seeded guest trial, so no search or AI call is made (see below).

## 5. The twelve scenarios (all in Stripe TEST mode, test cards only: 4242 4242 4242 4242 pays; closing the page abandons)

| # | Scenario | Pass means |
|---|---|---|
| 1 | Guest discovers businesses and saves an AI profile | Seeded trial: 10 businesses, one with a saved profile; `/trial/results` shows it |
| 2 | Guest creates an ALPA account | Sign-up succeeds; with email confirmation ON the page says to confirm |
| 3 | Guest businesses and profiles transfer | After the first sign-in the account's leads equal the trial's businesses, the saved profile is in `leads.light_profile`, the website facts are kept, none deleted |
| 4 | Selected plan survives signup and email confirmation | Choose Prospector signed out, sign up, open the confirmation link in the same browser, sign in: you land on checkout for Prospector, not the dashboard |
| 5 | Account completes Stripe test checkout | Pay with 4242; `/post-checkout` activates and opens the dashboard |
| 6 | Correct subscription activated | `profiles.plan` = the chosen plan, `plan_status` active, `stripe_subscription_id` matches Stripe; the webhook deliveries show 2xx |
| 7 | A second account cannot activate that session | Signed in as account B, open `/post-checkout?session_id=<A's session>`: "not found", B stays free; A unchanged |
| 8 | Repeated activation creates no duplicate | Reload the post-checkout page and replay the webhook event: still one subscription in Stripe and one in the profile |
| 9 | Existing leads survive checkout | Account with 10 leads (incl. imported) pays: all 10 remain, same ids |
| 10 | Abandoned checkout grants no paid access | Start checkout, close it: profile still free, no subscription in Stripe, leads intact, a new attempt works |
| 11 | Stale session cannot replace a subscription | Pay, cancel, pay again (new session); activating the FIRST session returns an error and leaves the newer subscription in place |
| 12 | Stripe outage | Restart the app with the Stripe blocker: My Leads still opens and lists every business, the plan is shown but `plan_verified` is false, a search is refused with "could not verify your subscription" and no research job is created |

Also verified in the same run: webhook signature rejection (wrong secret, unsigned and altered bodies through `curl`), and `GET /api/checkout/session` and activation refusing signed-out callers.

## 6. Cleanup and keeping data separate

- **Separation:** the test project, the test Stripe keys and `.env.stripe-test` are used only through that file; `check-isolation.mjs` must pass before any run and exits non-zero if the production project or a live key is present. Production Vercel variables are never edited for testing.
- **Test users:** delete in the dashboard (Authentication, Users) or with the admin API; `profiles`, `leads` and guest trials for those ids are removed with a one-line `delete ... where user_id in (<test ids>)` in the TEST project. Or delete the whole test project, which removes everything at once.
- **Test subscriptions and customers:** in Stripe test mode, cancel with `stripe subscriptions cancel <id>` and delete customers with `stripe customers delete <id>`; or use the dashboard's "Delete all test data" for the test environment.
- **Usage:** the test database holds its own usage rows; delete them with the test users, or truncate the test project's usage tables.
- **Credentials:** the test secret key can be rolled in the Stripe dashboard (API keys, Roll key) and a test webhook endpoint or listener simply stopped; the Supabase test keys die with the project (or can be rotated in Project settings, API). `.env.stripe-test` is git-ignored; delete the file when finished.
